# Tik-Talk: план розробки

## Мета та межі

Реалізувати Angular-застосунок Tik-Talk відповідно до погоджених екранів Figma та реально доступних можливостей API курсу: `https://icherniakov.ru/yt-course/`.

**У межах:** дизайн-токени та оболонка, автентифікація, пошук користувачів і картки, перегляд/редагування профілю, список чатів і діалог — якщо відповідні endpoints підтримують ці дії, тестування та фінальна перевірка інтерфейсу.

**Поза межами:** встановлення інструментів/скілів і створення правил, WebSocket, функції бекенду, яких немає в API. Опитування сервера не додавати без підтвердження підтримки API та узгодження частоти/умов зупинки. Якщо API не підтримує частину функціональності, зафіксувати обмеження й погодити спрощений UX до реалізації.

## Вихідний стан і технічні рішення

- Angular `^22.2`, standalone-компоненти, TypeScript `~6.0`, SCSS, Vitest/Angular test runner — згідно з `package.json`.
- Роутинг уже підключений, але `src/app/app.routes.ts` порожній; `provideHttpClient` ще не налаштований.
- Є `ProfileCard`, але він поки відображає статичні дані. Глобальні стилі містять лише базові кольори.
- Шлях до асетів уже виправлений на `public/assets/imgs/`; повторне перейменування не є окремою задачею. Перевірити використання шляху в інтерфейсі.
- Тест застосунку розташований у `src/app/app.spec.ts` (не `app.component.spec.ts`); перевірити/оновити тест, якщо він досі очікує стартовий заголовок-заглушку.
- Сервіси ізолюють HTTP і мапінг API-моделей у моделі UI. Базову адресу API та конфігурацію не дублювати в компонентах.
- Використовувати Signals для локального реактивного стану. Для нових форм Angular 22 — Signal Forms; якщо вимоги або сумісність API цього не дозволяють, до реалізації зафіксувати обґрунтований вибір Reactive Forms.
- Вибір способу зберігання токенів визначити за підтримкою бекенду. Не закладати чутливі токени в `localStorage` без окремої оцінки ризику; не вважати guard заміною серверної авторизації.

## Етапи реалізації

### 0. Уточнення дизайну та API-контракту

**Роботи:**
- Перевірити потрібні вузли Figma (відомий вузол пошуку: `4010-7817`), зібрати список екранів, навігацію, адаптивні стани й необхідні стани компонентів.
- Перевірити документацію/відповіді API для login, пошуку, профілю, оновлення профілю та чатів: HTTP-методи, payload, авторизацію, пагінацію, помилки й наявність endpoints.
- Уточнити поля профілю та розбіжності між моделями API і UI. Не вважати початковий приклад `Profile` остаточним контрактом.
- Зафіксувати результати в плані: матриця «екран/сценарій → endpoint → метод/поля/авторизація → підтримується/не підтримується», перелік станів екранів і список відкритих рішень.
- Позначити функції, які не підтримує API, як поза MVP; погодити спрощений UX до початку залежної реалізації.

**Готово, коли:** матриця API та перелік маршрутів/станів переглянуті; кожен сценарій MVP має підтверджений контракт або узгоджене спрощення; жодна невідома можливість не лишається неявним припущенням.

### 1. Фундамент, дизайн-токени та оболонка

**Роботи:**
- Перевірити поточні зміни асетів, імпорти й базові стилі; не повторювати вже зроблене виправлення шляху.
- На основі Figma визначити кольори, типографіку, відступи, радіуси та стани; оформити узгоджені CSS-змінні в `src/styles.scss`.
- Налаштувати `provideHttpClient` та interceptor-підключення в `src/app/app.config.ts` у межах підтвердженої схеми автентифікації.
- Створити layout авторизованої зони, sidebar і маршрути-заглушки для погоджених екранів; передбачити активний пункт навігації та адаптивну поведінку.

**Готово, коли:** оболонка й маршрути відповідають узгодженій карті; кожен маршрут відкривається без помилки; токени стилів відповідають погодженій палітрі; HTTP-клієнт налаштовано один раз. До етапу 0 можна виконувати лише роботу, що не залежить від невирішених дизайн/API-рішень.

### 2. Автентифікація та захищена навігація

**Роботи:**
- Реалізувати екран входу згідно з Figma та `AuthService` відповідно до підтвердженого контракту API.
- Додати interceptor для авторизованих API-запитів і функціональний guard; не прикріплювати токен до сторонніх доменів.
- Реалізувати стани входу: очікування, помилка API/валідації, успіх, вихід і відновлення сесії відповідно до можливостей бекенду.
- Після входу повертати користувача на запитаний захищений маршрут або погоджену стартову сторінку.

**Готово, коли:** успішний вхід відкриває захищену зону, гість перенаправляється на login, помилки показані користувачу, а сесія обробляється згідно з реальним механізмом API.

### 3. Пошук і картки профілів

**Роботи:**
- Реалізувати сторінку пошуку та `ProfileService` за підтвердженими endpoints і моделлю.
- Перетворити `ProfileCard` зі статичного шаблону на повторно використовуваний компонент із типізованим `input()` і коректним альтернативним текстом/зображенням-заповнювачем.
- Показувати стани завантаження, помилки, непорожнього результату та відсутності збігів; уникати застарілих результатів при швидкій зміні запиту.
- Якщо API підтримує серверний пошук або пагінацію — використовувати їх; не підміняти контракт локальною фільтрацією без погодження.

**Готово, коли:** реальний результат API відображається в картках, введення пошуку дає очікуваний результат, а всі визначені стани доступні й перевірені.

### 4. Перегляд та редагування профілю

**Роботи:**
- Реалізувати погоджені маршрути профілю (власний/інший користувач — лише якщо підтверджені дизайном та API) і сторінку редагування.
- Створити типізовану форму з валідацією, початковими значеннями, станом збереження та відображенням помилок API.
- Надсилати лише підтримувані API поля; після успішного збереження синхронізувати профіль у видимих частинах застосунку.

**Готово, коли:** завантажені дані відповідають API, невалідну форму не можна зберегти, помилка сервера не втрачає введені дані, а успішне збереження відображається без перезавантаження сторінки.

### 5. Чати (залежить від етапу 0)

**Роботи:**
- Реалізувати список чатів, історію конкретного діалогу та надсилання повідомлення лише для підтверджених endpoints.
- Обробити завантаження, порожній список, помилки та стани відправки; визначити поведінку після успішного відправлення.
- Реалізовувати polling тільки за підтвердженої потреби: визначити інтервал, зупинку при виході зі сторінки/втраті сесії та відсутність дублювання запитів.

**Готово, коли:** список та діалог працюють на API, стани помилок/порожнього вмісту зрозумілі, а спосіб оновлення повідомлень не перевищує узгоджені можливості бекенду.

### 6. Перевірки, доступність і фінальне приймання

**Автоматизовані перевірки:**
- Unit-тести сервісів через HTTP testing utilities для успішних відповідей і помилок.
- Тести guard/interceptor, критичних станів сторінок, картки профілю та валідації форми.
- Перевірка навігації та основних потоків: вхід → пошук → профіль → редагування; чати — якщо підтримані API.
- Оновити `src/app/app.spec.ts`: замінити перевірку стартового заголовка-заглушки на перевірку актуальної оболонки.
- Запустити наявні тести (`npm test`) і production build (`npm run build`); виправити пов'язані з реалізацією помилки.

**Ручне приймання:**
- Звірити погоджені екрани зі Figma для десктопного й мобільного viewport; перевірити адаптивність, фокус клавіатури, видимість фокуса, підписи контролів та контраст ключових текстів.
- Перевірити гостьовий доступ, порожній пошук, відсутній аватар, помилки/повільну відповідь API та порожні чати, якщо вони в межах підтриманого сценарію.
- Переконатися, що в інтерфейсі немає необроблених помилок або статичних демонстраційних даних замість реальних.

**Готово до завершення, коли:** кожен погоджений сценарій MVP має зафіксований результат перевірки; `npm test` та `npm run build` завершуються успішно; невирішені обмеження API задокументовані; ключові стани відповідають погодженій Figma.

## Рекомендації та ризики

1. Починати з етапу 0: API курсу може не підтримувати частину функцій, особливо повноцінний діалог або редагування профілю.
2. Не називати візуальну відповідність «pixel-perfect» критерієм без погоджених viewport, шрифтів, станів і способу порівняння; приймати її за конкретними екранами та сценаріями.
3. Не закладати завершеність лише за успішним build: перевіряти поведінку, помилки мережі, доступність і автоматизовані тести.
4. Підтримувати план актуальним: після етапу 0 уточнити залежності/критерії, а виконані етапи позначати лише після перевірки критеріїв «Готово».

## Фактичний статус на 28.10.2026

Курсовий API та його документація повертають `404`, тому функціональність, що залежить від живого сервера, замінена локальним демо-режимом на прохання користувачки. Це рішення дозволяє перевіряти основні сценарії в одному браузері, але не надає серверної автентифікації чи синхронізації між пристроями.

- Етап 1: оболонка та маршрути вже були створені до цієї роботи.
- Етап 2: додані реєстрація, вхід, вихід, відновлення сесії та guard. Акаунти й сесія зберігаються у `localStorage`; паролі не зберігаються відкритим текстом — використовуються окремі випадкові солі та PBKDF2-SHA-256. Це не захист від модифікації даних у браузері й не заміна бекенду; не використовувати справжні/повторно використані паролі.
- Для заповнення інтерфейсу додані три демонстраційні профілі й стартові вхідні повідомлення для нового акаунта; демодані мають помітку в інтерфейсі та не можуть використовуватися для входу. Формат сховища оновлюється з версії 1 до 2 без видалення наявних локальних акаунтів.
- Етап 3: реалізовані пошук локальних профілів, картки, переходи до профілю та початку чату; додані порожній стан і фільтрація.
- Етап 4: реалізовані перегляд власного та локальних профілів і редагування власного профілю з валідацією та локальним збереженням.
- Етап 5: реалізовані список локальних діалогів, обмін повідомленнями між акаунтами в цьому сховищі та порожній стан. Оновлення через polling не використовується; окремі пристрої не синхронізуються.
- Етап 6: unit-тести сервісів та guard для локальної реєстрації, перевірки паролів, сесії, профілів і повідомлень. `npm test -- --watch=false` (6 тестів) і `npm run build` завершилися успішно. Ручне звірення з Figma та проходження сценаріїв у браузері не виконувалися.
